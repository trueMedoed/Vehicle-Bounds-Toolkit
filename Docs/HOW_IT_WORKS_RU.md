# Как работает ME Vehicle Bounds Toolkit

## Краткая схема

Toolkit использует три разных источника данных:

```text
каталоги игры
    ↓
список префабов, которые должны быть проверены

ME_VBT_VehicleBoundsFixture.ent
    ↓
размещённые экземпляры префабов, которые фактически проверяются

Candidate / Baseline snapshot
    ↓
измеренные bounding boxes и результаты сравнения
```

Эти источники не дублируют друг друга. Они отвечают на разные вопросы:

- **каталог** — что должно входить в проверку;
- **fixture** — что фактически размещено и измеряется;
- **snapshot** — какие bounds были получены и изменились ли они.

## Что находится в каталогах

Каталоги фракций игры содержат ссылки на префабы техники, например:

```text
{GUID}Prefabs/Vehicles/Wheeled/...
```

Для каждой записи Toolkit определяет:

- канонический путь префаба;
- фракцию;
- базовый тип техники.

Каталог отвечает только за состав набора. Наличие ссылки в каталоге ещё не означает, что этот префаб был размещён в тестовой сцене или измерен.

## Что такое fixture

`ME_Vehicle_Bounds_Toolkit/Worlds/ME_VBT_VehicleBoundsFixture.ent` — это контролируемая тестовая сцена World Editor с экземплярами префабов техники.

В сцене каждый измеряемый экземпляр имеет помеченный root. Marker-компонент хранит канонический путь соответствующего префаба и связывает экземпляр с записью каталога.

Fixture не содержит копий файлов префабов. Он содержит **размещённые экземпляры** префабов, загруженные движком в мире.

## Зачем нужны экземпляры в мире

Измерение выполняется для сущности, загруженной в World Editor, а не только для строки с путём к `.et`-файлу:

```text
файл префаба
    ↓ разрешение наследования и overrides
экземпляр сущности в мире
    ↓ WorldEditorAPI
геометрия экземпляра и дочерних сущностей
    ↓
фактический bounding box
```

При работе с экземпляром учитываются данные, которые могут быть распределены по иерархии префаба:

- наследование префабов;
- дочерние сущности;
- `MeshObject` и другие визуальные компоненты;
- колёса, башни, антенны и дополнительное оборудование;
- overrides конкретного экземпляра;
- итоговая трансформация сущности.

Поэтому простого чтения пути префаба из каталога недостаточно, чтобы получить тот же результат, который видит World Editor.

## Проверка покрытия

Команда `VBT: Validate fixture coverage` сравнивает два набора:

```text
объединение записей каталогов
        ↕ точное соответствие
marker roots в fixture
```

Проверяются, в частности:

- наличие всех обязательных каталогов и scopes;
- принадлежность каждого префаба одной фракции и одному базовому типу;
- отсутствие дубликатов и конфликтов;
- наличие соответствующего marker root для каждого префаба;
- отсутствие лишних marker roots;
- совпадение канонических путей и количества записей.

Например:

```text
catalog=164 markers=146
```

означает, что каталог требует проверки 164 префабов, а в fixture подготовлено только 146 marker roots. Это не ошибка отсутствия файлов игры. Это означает, что 18 экземпляров ещё не добавлены в тестовую сцену.

## Измерение bounds

Команда `VBT: Generate bounds snapshot` после успешной проверки покрытия:

1. находит каждый marker root;
2. учитывает root и его дочерние сущности;
3. получает world-space AABB через World Editor;
4. переводит минимальную и максимальную точки относительно root;
5. строит сгруппированный snapshot:

```text
faction → vehicle type → prefab
```

Результат сохраняется в Candidate. Затем Candidate проверяется после повторной загрузки и сравнивается с Baseline.

## Candidate и Baseline

### Candidate

Candidate создаётся из текущей версии игры и текущего состояния fixture:

```text
Configs/Generated/ME_VBT_VehicleBoundsPerPrefabCandidate.conf
```

Он показывает результат текущего измерения и может быть перезаписан следующим запуском генератора.

### Baseline

Baseline — это вручную принятый эталон:

```text
Configs/Generated/ME_VBT_VehicleBoundsPerPrefabBaseline.conf
```

Он нужен для регрессионной проверки. Если после обновления игры, префаба или fixture bounds изменились, Toolkit сообщает разницу между Candidate и Baseline.

## Почему нельзя просто пройти каталог

Если требуется только проверить, что все ссылки из каталога указывают на существующие ресурсы, fixture действительно не нужен.

Но Toolkit проверяет более широкое утверждение:

> Для каждого выбранного префаба существует подготовленный экземпляр, который можно измерить одинаковым способом, а его результат можно сравнить с принятым эталоном.

Для этого нужны загруженный мир и `WorldEditorAPI`.

## Почему плагины используют World Editor

Текущая реализация работает с живой сценой через:

```c
WorldEditor worldEditor = Workbench.GetModule(WorldEditor);
WorldEditorAPI api = worldEditor.GetApi();
```

Поэтому операции, которые читают или изменяют fixture, выполняются в модуле World Editor:

- preflight имён fixture roots;
- применение канонических имён;
- проверка покрытия каталогов и marker roots;
- измерение bounds;
- создание snapshot.

Префабы и каталоги читаются из ресурсов игры, но сами измеряемые сущности берутся из открытой fixture-сцены.

## Можно ли отказаться от ручной fixture

Да, существуют два возможных направления:

1. Автоматически создавать временную сцену из каталога, размещать в ней все префабы, выполнять измерения и удалять сцену.
2. Реализовать отдельную загрузку и анализ `.et`-ресурсов без World Editor.

Первый вариант всё равно использует World Editor, но может убрать ручное поддержание fixture. Второй вариант потребует самостоятельно разрешать наследование, дочерние сущности и overrides префабов. Кроме того, результат может отличаться от измерения, которое выполняет World Editor.

Поэтому текущая fixture-сцена является контролируемым и воспроизводимым набором тестовых данных, а не дубликатом файлов игры.

## Итог

```text
Каталог:
  какие префабы должны быть проверены

Fixture:
  какие экземпляры реально размещены и измеряются

Snapshot:
  какие bounds получены

Baseline:
  какие bounds считаются принятыми
```

Если каталог изменился, fixture нужно синхронизировать с ним до создания нового snapshot. Если bounds изменились, нужно изучить diff и только после проверки вручную принять новый Baseline.
